SPA.cz Partner · mobile app proposal A

Hotel operations designed as a focused mobile app

A clickable Czech and English app prototype for daily reservation, availability, offer, rate and billing work. The existing spa/spacz_web panel is the source of functionality and business rules; this artifact does not propose a replacement desktop web interface. Its visual system comes from the supplied Szallas design-system export and the confirmed SPA.cz brand values.

8 product areas 390 × 844 phone viewport CZ + EN 24 editable Figma frames

The proposal

Variant A is the current proposal. It turns the broad existing web panel into a focused operating sequence for a phone. There is no desktop web proposal in this artifact and there are no superseded visual variants in this round.

This is a working prototype, not a collection of pictures. Start on Dashboard, open Reservations, inspect a reservation, then review its Billing item. The second path runs from Dashboard through Availability to Offer and Rate edit. Selected demo state carries across those screens.

What to try

Filter the reservation queue, open a reservation, switch an availability day, follow the offer-to-rate path, and test both billing decisions. In the floating prototype panel, compare permissions, channel-manager mode, density, fixture volume and test-property mode.

Business rules, not visual taste

  • An active channel manager makes availability read-only in the partner panel — AvailabilityOverviewController.php:19–32 and availability-overview/index.tpl:1–5.
  • Billing approval requires an eligible account; dispute additionally requires a reason and a positive price — ajax/BillingController.php:43–112.
  • Reservation detail is scoped to the selected hotel/product and assembles rooms, guests, status, voucher, cancellation, package, contact and invoice context — ReservationsController.php:46–157.
  • The public fixture is SPA HOTEL ČAJKOVSKIJ: 3 days, 2 nights, from 3,577 CZK, check-in 14:00 and check-out 10:00 — verified on the public package page on 7 August 2026.
  • The prototype uses deterministic fixture data only. No production database dump or local copy of the supplied user row is required.

Comment privacy

The comment layer is included but currently disabled because comments.config.json is intentionally absent. When configured, Google-signed-in comments use the selected third-party Firebase project and threads are stored there, not in these static files. Reviewer allowlists are required. Comment dumps contain reviewer names and email addresses; keep them private and never commit or publish them.
